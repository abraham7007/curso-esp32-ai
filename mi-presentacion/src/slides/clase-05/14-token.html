05 · Seguridad y estado

Token fuera del código y transmitido cifrado

El token da acceso a los datos y a las órdenes. Sigue el esquema de la clave de 4 · 19, y además se verifica el certificado.

Pregunta de predicción: si el token ya se subió al repositorio, ¿basta con borrarlo? Recoger respuestas antes de leer la última línea.

Respuesta: no. El token queda en el historial; hay que regenerarlo y, si la consola no ofrece regenerarlo, borrar el dispositivo y crear otro, con token nuevo.

Es el mismo esquema que la clave de OpenWeatherMap (sesión 4 · 19): secrets.h fuera de git, plantilla versionada y una comprobación de presencia del archivo (__has_include) para que el proyecto recién clonado compile y el servidor responda «Invalid auth token». Lo propio de Blynk: las credenciales deben existir antes de cargar su cabecera, porque la biblioteca comprueba en ese momento si BLYNK_TEMPLATE_ID está definido.

Abajo, el motivo del puerto 443: el primer mensaje lleva el token completo, y con BlynkSimpleEsp32.h se transmite en claro por el puerto 80, al alcance de cualquier equipo de la misma red. La versión SSL carga el certificado raíz incluido en la biblioteca (setCACert) y lo comprueba; a diferencia de 4 · 11, un servidor suplantado tampoco obtiene el token.

Para estudiar

En la práctica

Copiar include/secrets.example.h como include/secrets.h y pegar en él los tres valores de la pestaña «Device Info»: Template ID, Template name y Auth token. Cabecera del mensaje: tipo 1 B, id 2 B, longitud 2 B (lámina 07).

Dónde aparece

Ejemplo 19: .gitignore con include/secrets.h y la cabecera BlynkSimpleEsp32_SSL.h.

Errores frecuentes

  • Cargar la cabecera de Blynk antes que secrets.h: compila, pero el Template ID ya no se envía al servidor.
  • Compartir una captura de «Device Info» con el token visible.
