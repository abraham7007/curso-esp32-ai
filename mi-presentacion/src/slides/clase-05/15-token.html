Protección del token en el repositorio, la red y la placa

El token es la llave del dispositivo: quien lo tiene lee sus datos y le envía órdenes. Se guarda fuera del código, viaja cifrado y cada placa tiene el suyo.

Presentar el token como la llave del dispositivo: abre la puerta a sus datos y a sus órdenes, así que se guarda, se transporta y se reparte como una llave.

Repositorio: es el mismo esquema que la clave de OpenWeatherMap (sesión 4, lámina 19). Solo secrets.h queda fuera de git; quien clona el proyecto recibe la plantilla, compila igual y el servidor responde «Invalid auth token» hasta que coloca su propio token.

Red: el primer mensaje de la conexión lleva el token completo. Sin cifrar, cualquier equipo de la misma red lo lee; el ejemplo 19 usa la versión cifrada, que además comprueba el certificado del servidor, de modo que un servidor suplantado tampoco obtiene el token.

Pregunta de predicción: si el token ya se subió a un repositorio público, ¿basta con borrarlo del archivo? Respuesta: no; el historial lo conserva y hay que sustituirlo por uno nuevo (paso 1).

Para estudiar

En la práctica

Copiar include/secrets.example.h como include/secrets.h y pegar en él los tres valores de la pestaña «Device Info»: Template ID, Template name y Auth token. Las credenciales deben definirse antes de cargar la cabecera de Blynk. Cabeceras: BlynkSimpleEsp32.h (puerto 80, sin cifrar) y BlynkSimpleEsp32_SSL.h (puerto 443, TLS con el certificado raíz incluido en la biblioteca). Para un dispositivo creado a mano, docs.blynk.io no describe cómo regenerar el token: la vía segura es borrar el dispositivo y crear otro desde la plantilla, que recibe un token nuevo.

Dónde aparece

Ejemplo 19: .gitignore con include/secrets.h y la cabecera SSL de Blynk.

Errores frecuentes

  • Cargar la cabecera de Blynk antes que secrets.h: compila, pero el Template ID no llega al servidor.
  • Compartir una captura de «Device Info» con el token visible.
  • Añadir secrets.h al .gitignore después de subirlo, cuando git ya lo sigue.
