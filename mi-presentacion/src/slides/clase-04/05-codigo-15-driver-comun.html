La hora del código Ejemplo 15

Dos sensores distintos tras la misma interfaz

Sobre el proyecto. Una clase base Sensor con los métodos que toda fuente debe ofrecer, implementada dos veces: para una entrada analógica y para un sensor I²C. El archivo principal trabaja con un puntero a la base y no sabe cuál tiene delante.

Conceptos clave

Un método virtual puro declara qué debe existir sin decir cómo: obliga a cada implementación a proporcionarlo. El archivo principal guarda un puntero a la clase base y la llamada se resuelve en ejecución sobre el objeto real. Que la interfaz incluya isReady() y status(), y no solo read(), es lo que permite distinguir un valor válido de uno que no lo es.

Prompt para el asistente

1. Proyecto. Crea un proyecto nuevo de PlatformIO para la placa esp32dev con el framework Arduino, con lib/Sensor/ para la interfaz y sus dos implementaciones. 2. Firmware. Sensor es una clase base abstracta con begin(), read(), isReady() y status() virtuales puros. Impleméntala en SensorAnalogico (GPIO 32) y SensorI2C. En main.cpp declara un puntero Sensor* y trabaja solo a través de él: cambiar de fuente debe ser cambiar una única línea. Emite por el puerto serie a 115200 baudios «[APP] fuente=X valor=N.N C estado=OK», con el mismo formato para ambas. 3. Simulación. Añade la simulación de Wokwi con el potenciómetro en el GPIO 32 y un sensor I²C en SDA 21 y SCL 22. 4. Diagramas. Entrega dos en Excalidraw. El diagrama de flujo de una lectura, con la comprobación de estado antes de usar el valor. Y un diagrama de clases con la base y sus dos implementaciones, marcando qué conoce el archivo principal.

Análisis

Las dos mitades de la traza son idénticas en formato y solo cambia el campo fuente: el código que las emite es el mismo. Comprobar en el proyecto propio que cambiar de fuente toca una sola línea. Si hubiera que tocar además la parte que imprime o la que decide, la aplicación depende de la implementación y no de la interfaz.
