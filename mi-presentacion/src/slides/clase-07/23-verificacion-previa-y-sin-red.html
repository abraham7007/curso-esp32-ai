02 · Protocolo HTTP y APIs REST

Verificación previa de la API y operación sin conectividad

Verificar la API antes de escribir firmware

La petición se prueba primero desde el navegador o desde un cliente de escritorio, hasta obtener la respuesta esperada. Solo entonces se lleva al dispositivo.

Depurar a la vez el enlace de red y el código de la petición impide aislar la causa: un 401 puede deberse a la clave, al formato de la cabecera o a la ruta, y sobre el dispositivo las tres se ven igual.

Con qué comprobarlo

La barra del navegador basta para un GET sin cabeceras. Para lo demás, curl desde la terminal: muestra el código de estado, las cabeceras y el cuerpo, y su orden se traslada casi literalmente al firmware.

Comportamiento sin conectividad

Un dispositivo sin red no debe detenerse ni mostrar el último valor como si fuera actual. Las tres decisiones que hay que tomar antes de programar:

Qué conserva Último valor válido con su timestamp, para poder decir cuán antiguo es.
Cuándo lo declara caducado Un umbral explícito, propio de la magnitud: 15 min para temperatura exterior, 5 s para una consigna de control.
Qué sigue haciendo Adquirir y almacenar en local. La sesión 10 añade el envío diferido de lo acumulado.
$ curl -i -H "Authorization: Bearer $CLAVE" \ https://api.ejemplo.com/v1/estado HTTP/2 200 content-type: application/json x-ratelimit-remaining: 4998
